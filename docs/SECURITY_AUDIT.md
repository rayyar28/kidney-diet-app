# 系統檢查報告：發現的問題與修復

> 報告日期：2026-09-11
> 範圍：在正式對外試用前，對「拍照記錄飲食」核心功能與帳號系統做的一次全面檢查，
> 包含程式碼檢視與實際打 API 驗證。以下問題**全部已修復並重新測試通過**，
> 另有幾項屬於「已知、但暫不處理」的項目列在最後。

---

## 已修復的問題

### 1.（🔴 高風險）JWT 簽署金鑰還是預設的佔位字串

- **問題**：後端用來簽發登入憑證 (JWT) 的兩個金鑰，一直是範本裡的
  `change-me-access-secret` / `change-me-refresh-secret`，沒有換成真正隨機的值。
- **為什麼嚴重**：任何人只要知道（或猜到）這個字串，就能自己偽造出「任何一位病人」
  的登入憑證，等於直接繞過帳號密碼登入系統。而且這個問題發生時，App 正好透過
  Cloudflare Tunnel 對外公開著。
- **修復**：產生兩組隨機字串（各 48 bytes，base64 編碼）換掉，並在
  `backend/.env.example` 加上警告註解，避免以後又照抄預設值。
- **驗證**：換完金鑰後重新啟動後端，確認舊的登入憑證全部失效、重新登入正常取得新憑證。

### 2.（🟠 中風險）前端 token 過期時，自動換發會互相打架

- **問題**：Access token 過期後，前端會自動用 refresh token 換一組新的。但「歷史紀錄」
  頁面一次會同時打好幾個 API（清單 + 每張照片各一個請求），如果剛好這些請求同時
  遇到 token 過期，會**各自獨立**去呼叫換發。而 refresh token 的設計是「用一次就
  失效」，所以只有最先送達的那個換發會成功，其他幾個會拿著已經失效的 token 換發
  失敗，進而把剛剛才換好的新憑證**洗掉**，病人會無預警被登出。
- **修復**：改成「同時發生的換發請求共用同一個進行中的 promise」，確保同一時間
  只會真的送出一次換發請求，其他請求等這一次的結果就好。
- **驗證**：模擬多個請求同時觸發換發，確認只送出一次 `/auth/refresh`，且不會誤登出。

### 3.（🟠 中風險）Refresh token 內容完全相同時，資料庫寫入會直接炸掉

- **問題**：如果在同一秒內連續登入兩次（例如手滑點兩下登入按鈕，或多個裝置幾乎
  同時登入），因為 JWT 的時間戳記只有「秒」的精確度，兩次簽出來的 refresh token
  內容會**完全一樣**，導致存進資料庫時撞到「同一個 token 不能存兩次」的限制，
  整個登入請求會回傳伺服器錯誤 (500)。
- **修復**：幫每個 refresh token 加上一個隨機的唯一識別碼 (`jti`)，確保即使同一秒
  內簽發，內容也不會重複。
- **驗證**：同時發送 5 個登入請求，全部成功，沒有再出現資料庫錯誤。

### 4.（🟠 中風險）個人資料 API 不小心把密碼雜湊值回傳給前端

- **問題**：查詢個人資料的 API 為了方便，直接把整個使用者資料表的內容回傳，
  結果連 `passwordHash`（用 bcrypt 加密過的密碼）也一起送到前端了。雖然是加密過的，
  但正常情況下密碼雜湊值不應該離開伺服器，一旦流出就多了一個被離線暴力破解的風險。
- **修復**：改成明確指定要回傳哪些欄位，不再整包帶出。
- **驗證**：重新查詢個人資料 API，確認回應內容已經不含 `passwordHash`。

### 5.（🟡 低風險）登入、註冊沒有任何防暴力破解機制

- **問題**：密碼可以無限次嘗試，也可以無限次註冊帳號，沒有任何節流機制。
- **修復**：加上請求次數限制——同一來源 15 分鐘內最多嘗試登入 10 次、1 小時內
  最多註冊 5 次，超過會回應「請稍後再試」。
- **驗證**：連續送出 12 次錯誤登入，第 11、12 次確認被擋下（回應「請求次數過多」）。
- **已知限制**：目前是依「請求來源 IP」計算次數，但實際部署走 Cloudflare Tunnel
  時，後端看不到病人的真實 IP，等於所有人共用同一個額度。等正式部署到有標準
  反向代理的伺服器後，這個限制會自然消失，暫時算是可接受的過渡狀態。

### 6.（🟡 低風險）照片上傳失敗時，回應的錯誤代碼是錯的

- **問題**：上傳格式不對的檔案，或檔案超過 15MB 上限時，系統原本會回應
  「伺服器發生未預期的錯誤」(HTTP 500)，這在語意上是錯的——問題出在使用者上傳
  的檔案，不是伺服器壞了，應該回應 HTTP 400。
- **修復**：讓錯誤處理程式正確識別檔案上傳相關的錯誤，回應清楚的中文訊息
  （例如「照片檔案太大了 (上限 15MB)」）與正確的狀態碼。
- **驗證**：分別測試上傳純文字檔（假裝是照片）與超過 15MB 的檔案，兩者都正確
  回應 400 與對應訊息。

## 已知、但目前不處理的項目

這些不是立即的風險，先記錄下來，正式擴大使用前再評估：

| 項目 | 說明 |
|---|---|
| 沒有自動化測試 | 之後如果有人（包含我）改程式碼，比較容易在不知情的情況下改壞現有功能 |
| 沒有 email 驗證機制 | 任何人可以用任意 email 註冊帳號；短期試用沒關係，正式收案建議改成由衛教師預先建立帳號 |
| 照片格式驗證非 100% 防偽 | 目前靠檔案的 mimetype 加上實際用影像處理套件 (sharp) 試著解析，可以擋掉大部分偽裝，但不是滴水不漏的防護 |
| 大量同時上傳時的記憶體用量 | 目前上傳的照片會先整個讀進伺服器記憶體再處理，正常試用規模不會有問題，但如果未來同時有很多人一起上傳，可能需要改成串流處理 |
| 過期的 refresh token 不會自動清除 | 資料庫裡會持續累積過期的登入憑證紀錄，長期下來佔用的空間很小，但之後可以加一個定期清除的排程 |

## 關於資料庫與照片儲存空間

檢查過程中也一併確認了「病人資料量變大時，主機容量會不會爆掉」這個疑慮：

- **結構化資料庫**（帳號、用餐紀錄、點數等文字/數字資料）：以 20 位病人記錄 3 個月估算，
  總資料量大概是幾十 MB，幾乎不可能把主機塞滿。
- **真正會佔空間的是照片檔案**：同樣的估算下大約是 20~30 GB，是資料庫的數百倍。

系統目前已經把「照片存哪裡」這件事抽成一個獨立模組（`StorageService`），現在存在
主機本機磁碟，未來要換成雲端物件儲存（例如 Cloudflare R2）只要換掉這個模組的實作，
不需要更動其他程式碼或資料庫結構。**這次先不換**，等真正需要擴大規模時再處理即可。
