## 一、本週摘要

1. **資料庫從 PostgreSQL 換成 SQLite。** 主因是**專題/論文要跟合作對象一致**；順帶的好處是醫院那台電腦不必再安裝與維護一個資料庫服務，整個資料庫就是一個檔案。
2. **點數、連續天數、徽章改成在手機上計算。** 病人常常是離線的，而原本點數完全由伺服器算——拍完一餐、最想看到回饋的那一刻，畫面上只會寫「有網路時會幫你算」。對年長使用者來說，那等於做完一件事卻什麼回饋都沒有。
3. **登入後可以沿用試用時的紀錄**，但那些紀錄**不會上傳**（IRB 尚未核准）。這是本週比較難拿捏的一題，細節見 2.3。
4. **醫院部署手冊整個改寫**成 Docker + SQLite 的流程（903 → 752 行），並補上兩件會真的擋住進度、但原本沒寫的事。
5. **發了兩個 APK 版本**，而且從這週開始版本號才真的會跟著變（前三版的 versionCode 一直停在 1，護理師回報問題時無從判斷手上是哪一版）。
6. **卡住的決定仍然卡著**：後端放哪裡、以及還沒有一支實體 Android 手機做驗證。

## 二、本週完成的工作

### 2.1 資料庫改用 SQLite（10/06）

**為什麼換**：專題/論文需要跟對方的做法一致。這是外部需求，不是技術偏好。

**代價**（Prisma 的 SQLite 版本有兩個限制）：

- **不支援 enum**。schema 裡 10 個 enum 欄位改成字串。為了不失去「打錯字會被擋下來」這個保障，另外寫了 `backend/src/domain/enums.ts` 把常數與型別補回來，程式碼的寫法完全不用改，只是檢查從資料庫層移到了編譯期。
- **不支援 Json 欄位**。食物辨識模型的原始輸出改存 JSON 字串。

**好處**：醫院那台電腦不必再安裝 PostgreSQL、不必顧一個資料庫服務會不會開機自動啟動。整個資料庫就是 `backend/data/kidney.db` 一個檔案。

**兩個一定要知道的坑**（都已寫進文件）：

- 必須開啟 **WAL 模式**，否則有人在寫入時所有讀取都會被擋住。病人在診間同步是「上傳照片 → 寫紀錄 → 算點數」一連串寫入，同一時間還有別人在看紀錄頁，不開會互相卡住。
- **不能直接複製 `.db` 檔當備份**。WAL 模式下真正的內容分散在兩個檔案，在有人寫入時複製很可能拿到不完整的快照——而且不會當場發現，是還原的那天才發現。改用 `npm run backup:db`（走 SQLite 內建的 `VACUUM INTO`，不必停機）。

**驗證**：36 項帳號/密碼端到端檢查、158 項前端測試全部通過；另外針對這次轉換寫了一次性的腳本，實際跑完「拍照上傳 → 當日全勤獎勵 → 點數結算 → 軟刪除」整個流程，確認點數落在正確的數字上。

### 2.2 點數改成在手機上算（10/07，v0.4.0-trial）

**問題**：病人常常沒有網路（家裡沒 Wi-Fi、院內網路要回診才連得到）。原本點數完全由伺服器計算，所以離線時拍完一餐，慶祝畫面上**沒有任何數字**。

**做法**不是把計算整個搬到手機，而是：

```
顯示的數字 ＝ 伺服器算到的結果 ＋ 這支手機上還沒上傳的紀錄
```

**為什麼不整個搬到手機**：手機上已同步的舊紀錄會被定期清掉（只留最近 100 筆 / 60 天，否則手機容量會被吃光）。如果在手機上重算整段歷史，就會算不到被清掉的那些——**收案到後期，病人的點數會開始變少**。對病人來說那是最糟的一種錯誤。

伺服器仍然是研究資料的正式來源。手機只補上「伺服器還不知道的部分」，所以東西上傳完成之後，手機顯示的數字會自動收斂回伺服器的數字，兩邊不會對不起來。

**效果**：

| 情境 | 改之前 | 改之後 |
|---|---|---|
| 離線拍完餐前照 | 數字不動 | 立刻 +10 |
| 離線完成一餐 | 沒有任何數字 | 顯示總點數與連續天數 |
| 離線補上當天第三餐 | 看不到 | 當場拿到「完美的一天」徽章 |

### 2.3 登入後沿用試用時的紀錄（10/07，v0.5.0-trial）

**問題**：病人可能先用試用模式記錄了幾天，之後才拿到帳號。原本一登入，那幾天的紀錄在帳號裡就完全看不到了。

**衝突**：IRB 尚未核准，試用期間拍的照片不能進伺服器。而同步引擎是「依登入帳號的 id 撈資料」的，所以只要把紀錄搬進帳號，它們就會自動被排進上傳佇列。

**做法**：搬進帳號，但標記成「本機專屬」、**永遠不上傳**。這些紀錄照常出現在日曆與點數裡，卡片上標示「🧪 試用紀錄·不會上傳」，也不會被算進「等待上傳」的數字。

**登入後會先問一次**，不是自動搬：App 沒辦法分辨「試用的人」跟「登入的人」是不是同一位。衛教師常常先用自己的手機試用、之後才讓病人在同一支手機登入——那些測試照片不該混進病人的資料裡。選「不用」只會記下「問過了」，資料原封不動留在試用模式。

**代價要講清楚**：這些紀錄**只有手機裡這一份**，伺服器上沒有備份，解除安裝就沒了。這是「不上傳」的必然結果，已寫在發布說明裡。

### 2.4 醫院部署手冊改寫（10/06）

改寫成 Docker + SQLite 的流程，903 → 752 行。原本「要問資訊室什麼」「第一天怎麼測連線」「網路不通的替代方案」這幾章幾乎原封不動——那些跟用什麼技術安裝無關，而且是整份文件最有價值的部分。

補上兩件原本沒寫、但會真的擋住進度的事：

- **Docker Desktop 對大型組織要付費訂閱**，醫院一定超過門檻。這要併進「要問資訊室什麼」的清單。
- **Docker Desktop 是桌面程式，沒有人登入就不會啟動**。所以自動登入那個設定不是可有可無——它決定半夜強制重開機之後，隔天早上病人傳不傳得了資料。

另外加了一個警告：清空資料時**不要連 Caddy 的憑證資料夾一起刪**。那裡面是憑證私鑰，刪了等於換憑證，已經裝在所有病人手機上的 App 會**同時全部連不上**，只能重新打包、請每個人重裝。

### 2.5 其他（10/01）

- **登入憑證的有效期從 30 天改成 365 天**。原本病人兩個月沒開 App 就會被登出，而密碼是衛教師在收案時設的，病人多半根本不知道——等於直接卡住，要回診才能解決。這是為了收案能順利進行所做的取捨。
- **新增 `CLAUDE.md`**，把「程式碼裡看不出來的專案限制」寫成文件（例如：刪除一律是軟刪除、試用資料不能上傳、帳號是衛教師建的、介面在 375×667 不能需要滑動）。

## 三、過程中發現或修正的問題

| 問題 | 怎麼發現的 |
|---|---|
| 同步完成的瞬間，點數會掉 10 分再跳回來（約 0.4 秒） | 在瀏覽器裡每 25 毫秒取樣畫面上的數字才看到。原因是紀錄被標成「已上傳」的瞬間，伺服器的新數字還沒拿到，這一筆兩邊都不算 |
| 補拍餐後照時，畫面對「不會上傳的紀錄」承諾「有網路就會自動上傳」 | 實際在瀏覽器走完整個流程才發現，讀程式碼看不出來 |
| 啟動時設定 WAL 模式的指令用錯，後端每次開機就當掉 | 後端一啟動就掛。編譯完全沒有錯誤 |
| 改了資料庫欄位卻忘了重新產生 Prisma 的程式，執行時噴 500 | 同上，編譯不會報錯 |
| 前三個 APK 版本的 versionCode 一直停在 1 | 這次發版前檢查才注意到。影響是護理師在手機上看到的版本永遠一樣，回報問題時無法判斷手上是哪一版 |
| 舊的 Docker 指南叫人用 `prisma studio` 直接看資料 | 那會開在容器內沒有對外的埠號，根本連不到。改成把備份檔複製出來、在開發機上開 |
| 測試檔案有一個型別錯誤，但測試是綠的 | 測試工具不做型別檢查，是建置時才抓到 |

## 五、需要老師意見的決定

### 5.1 後端要放哪裡（第三週提出，仍未決定）

APK 裡的後端網址必須在打包時寫死，所以要先決定後端放哪。

**這週的進展**：改用 SQLite 之後，「自己架」這個選項變簡單很多——醫院那台電腦不必再安裝與維護資料庫服務，整個資料庫就是一個檔案，備份就是產生一個檔案帶走。部署手冊已經按照這個方向改寫完成。

**仍然卡著的是**：要不要買網域。沒有網域就無法設定寄信服務，email 找回密碼那條路等於不能用（不過衛教師當面開代碼本來就是主力，影響沒有想像中大）。

### 5.2 需要一支實體 Android 手機（上週提出，仍然需要）

相機、存相簿、完全離線冷啟動**都還沒在真實手機上驗證過**。程式會編譯、權限設定正確、也確認功能有打包進 APK，但 WebView 內的相機行為與實際存檔結果需要實機確認。目前所有驗證都是在桌機瀏覽器上做的。

### 5.3 IRB 核准之後，試用期間的紀錄要不要納入研究資料？（本週新增）

現在的做法是「帶進帳號但永不上傳」。如果之後認為那些紀錄也應該納入，程式上只要改一行就能讓它們正常上傳——但那等於把**在取得受試者同意之前拍的照片**納入研究資料。這是研究倫理的判斷，不是工程判斷，想請老師裁示。
