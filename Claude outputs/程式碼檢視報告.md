# 腎臟病飲食紀錄 App — 程式碼檢視報告

檢視對象：`rayyar28/kidney-diet-app`（Express + Prisma + PostgreSQL / React + Vite PWA）
檢視日期：2026-09-14

---

## 先講結論

整體架構是**明顯高於一般大學專題水準**的：資料表設計有想過研究需求、有軟刪除、有 event-sourced 點數帳本、有預留辨識結果的表、有寫文件、金鑰沒有進版控。這些都做對了。

但有幾個問題會**直接影響你研究資料的效度**，以及幾個會讓病人在真實使用時卡住的 bug。下面依嚴重度排。

## 🔴 嚴重：會毀掉研究資料的問題

### 1. `capturedAt` 是「病人按下選擇的那一刻」，不是真正的拍攝時間

`frontend/src/components/CameraCaptureField.tsx`：

```ts
function handleChange(e: ChangeEvent<HTMLInputElement>) {
  const file = e.target.files?.[0];
  const capturedAt = new Date();   // ← 這是「選好檔案」的當下時間
  ...
}
```

程式碼的註解自己承認了這件事，但影響被低估了。`<input accept="image/*" capture="environment">` 在手機上**不保證**開相機——iOS 和部分 Android 仍會讓使用者選「從相簿選擇」。一旦病人選了一張三小時前的舊照片：

- `capturedAt` = 現在
- `preMealAt` = 現在
- 你算出來的 `mealDurationSeconds` 是錯的
- 而你**完全無法從資料庫分辨**哪些筆是真的、哪些是補的

這對一篇要談「用餐時間」的研究是致命的。

**修法**：照片的 EXIF 裡就有真正的拍攝時間，而你後端已經在用 sharp 了，讀得到。

```ts
// photo.service.ts
const meta = await sharp(photo.buffer).metadata();
// meta.exif 是 Buffer，用 exif-reader 解析
// 取 exif.Photo.DateTimeOriginal
```

建議在 `Photo` 表加三個欄位：

```prisma
exifCapturedAt   DateTime?  // EXIF DateTimeOriginal，沒有就是 null
exifRaw          Json?      // 完整 EXIF，未來要重新分析時不用重跑
captureSource    CaptureSource  // LIVE_CAMERA / GALLERY / UNKNOWN
```

`captureSource` 的判斷邏輯可以很簡單：`exifCapturedAt` 存在且與 `capturedAt` 相差 < 60 秒 → `LIVE_CAMERA`；相差很大 → `GALLERY`；沒有 EXIF → `UNKNOWN`。

這樣你在寫論文時可以說「我們排除了 N 筆非即時拍攝的紀錄」，而不是假裝所有資料都乾淨。**這一項是這次檢視裡最重要的建議。**

### 2. 照片原圖直接落地，EXIF 裡的 GPS 座標完整保留

`schema.prisma` 第 197 行寫著：

```prisma
// 裝置資訊 (研究照片品質差異用，不含任何精確定位資訊)
deviceUserAgent String?
```

但 `photo.service.ts` 是把 `photo.buffer` 原封不動存進 storage：

```ts
const storageKey = await storageService.save({ buffer: photo.buffer, keyHint });
```

手機拍的照片 EXIF 裡有 `GPSLatitude` / `GPSLongitude`。**你的資料庫裡現在躺著每個病人每一餐的精確座標**——也就是他家的地址、他常去的餐廳、他去洗腎的醫院。註解說「不含定位資訊」，實際上含。

這在 IRB 審查會被抓，而且是應該被抓的。

**修法**：先把 EXIF 完整讀出來存進 `exifRaw`（研究用，存在資料庫有存取控制），再把**寫進檔案系統的那份**去識別化：

```ts
// 讀 metadata 之後、save 之前
const sanitized = await sharp(photo.buffer)
  .rotate()                    // 順便解決下面第 3 點
  .withMetadata({ exif: {} })  // 清空 EXIF
  .toBuffer();
await storageService.save({ buffer: sanitized, keyHint });
```

或至少：在同意書明確寫「我們會蒐集照片的位置資訊」，並在 schema 註解改成誠實的描述。

### 3. `widthPx` / `heightPx` 記錄的是旋轉前的尺寸

```ts
metadata = await sharp(photo.buffer).metadata();
widthPx: metadata.width,
heightPx: metadata.height,
```

sharp 的 `.metadata()` 回傳的是**檔案裡實際儲存的**寬高，不套用 EXIF Orientation。iPhone 直向拍的照片，檔案裡存的是 4032×3024（橫的），靠 `orientation: 6` 標記讓看圖程式轉 90 度。

結果：你資料庫裡幾乎所有 iPhone 照片都被記成「橫向」。之後你要分析「直/橫向對辨識準確率的影響」，資料是錯的；之後餵進辨識模型，如果沒做 auto-orient，模型看到的是躺著的食物。

**修法**：`sharp(buffer).rotate()` 之後再取 metadata，並額外存 `exifOrientation`。

## 🟠 重要：病人實際會遇到的 bug

### 4. 上傳流程沒有包在 transaction 裡 → 會產生「幽靈紀錄」

`meals.routes.ts` 的 `/pre-meal`：

```ts
const mealRecord = await prisma.mealRecord.create({...});   // ①
const photo = await ingestPhoto({...});                      // ② 可能丟 400
await awardPreMealPoints(userId, mealRecord.id);             // ③
```

如果 ② 失敗（照片格式 sharp 解不開、磁碟寫入失敗），①已經寫進去了。病人會在首頁看到一筆 `AWAITING_POST_PHOTO` 的紀錄，**但它沒有餐前照，而且沒有任何 API 可以補拍**，只能放棄。

而 ② 失敗是很容易發生的——見下一點。

**修法**：

```ts
await prisma.$transaction(async (tx) => {
  const mealRecord = await tx.mealRecord.create({...});
  const photo = await ingestPhoto({ tx, ... });
  await awardPreMealPoints(tx, userId, mealRecord.id);
  return { mealRecord, photo };
});
```

檔案寫入本身無法 rollback，所以順序應該是：先解析驗證 → 開 transaction 寫 DB → 最後寫檔案；或寫檔案失敗時補一個 `fs.unlink` 的 cleanup。

### 5. 接受 HEIC，但 sharp 很可能解不開

```ts
const ALLOWED_MIME_TYPES = new Set([
  "image/jpeg", "image/png", "image/webp", "image/heic", "image/heif"
]);
```

sharp 的預先編譯 binary（`npm install sharp` 拿到的那個）因為 HEVC 授權問題，**預設不含 HEIF 解碼**。所以 HEIC 檔會通過 `fileFilter`，然後在 `sharp(buffer).metadata()` 炸掉，回一個 400「無法解析這張圖片，請確認檔案是有效的照片格式」——病人明明拍的就是照片，會非常困惑。而且會留下第 4 點的幽靈紀錄。

iPhone 使用者從**相簿**選照片時，給的就是 HEIC。

**修法**（擇一）：

- 在前端用 `canvas` 把任何格式先轉成 JPEG 再上傳（順便解決檔案太大的問題）
- 或從 `ALLOWED_MIME_TYPES` 拿掉 HEIC/HEIF，並給一個看得懂的錯誤訊息
- 或確認你的部署環境 sharp 有 HEIF 支援（`sharp.format.heif.input.buffer`）

請務必**拿一支 iPhone 實際測一次從相簿上傳**。

### 6. 沒有縮圖，歷史頁會把原圖全部抓一遍

`AuthedImage` 每一張都打 `/api/photos/:id/file` 拿完整原圖，而上傳上限是 15MB。歷史頁一次列 20 筆 × 2 張照片 = 最多 600MB。病人用 4G 開歷史頁會直接卡死。

**修法**：上傳時用 sharp 額外產一張 512px 的縮圖（`thumbnailStorageKey` 欄位），列表用縮圖、詳情頁才載原圖。

### 7. 忘記拍餐後照時，App 不會提醒

你的需求 3 要求「餐前 + 餐後」才能算出用餐時間，但目前沒有任何機制催病人回來拍。實務上這會是你**資料完整率最大的殺手**——很多筆會永遠停在 `AWAITING_POST_PHOTO`。

PWA 可以用 Notification API + Service Worker 做本地提醒（餐前照上傳後 30 / 60 分鐘各推一次）。這不難做，但對資料完整率的影響很大，值得排進去。

## 🟡 資料正確性的小 bug

### 8. 里程碑徽章用 `===` 比對，會漏發

```ts
const completedCount = await prisma.mealRecord.count({...});
if (MEAL_COUNT_MILESTONES.includes(completedCount)) { ... }
```

只有「剛好等於 10/50/100/200」那一瞬間才會發。如果兩筆紀錄幾乎同時完成（離線補傳、重複送出），count 從 9 直接跳到 11，這個徽章**永遠拿不到**。`checkBreakfastBadge` 也一樣。

**修法**：改成 `completedCount >= milestone` 然後靠 `UserBadge` 的 unique 擋重複——反正 `awardBadgeIfNew` 已經會擋了。

### 9. 「今日三餐全勤」的時區基準混用

```ts
const alreadyAwarded = await prisma.pointsLedgerEntry.findFirst({
  where: { reason: DAILY_ALL_MEALS_BONUS,
           createdAt: { gte: dayStart, lt: dayEnd } },  // ← createdAt 是伺服器時間
});
```

`dayStart` / `dayEnd` 是用**病人裝置時區**算的當地日界線，但 `createdAt` 是**伺服器**寫入時間。在台灣（UTC+8）這兩個差 8 小時，晚上 8 點之後完成的第三餐，判斷會落到錯誤的日子，導致重複發獎或漏發。

**修法**：`PointsLedgerEntry` 加一個 `localDateKey String?`（`"2026-09-14"`），直接用字串比對，不要用時間範圍。

### 10. `mealDurationSeconds` 沒有上限檢查

只檢查了「餐後不能早於餐前」，沒檢查上限。病人隔天才想起來補拍餐後照，就會產生一筆「這一餐吃了 19 小時」的資料。

**修法**：後端拒絕超過（例如）4 小時的，或照收但加一個 `isDurationOutlier Boolean` 標記，讓研究分析時可以過濾。後者對研究比較友善。

### 11. 軟刪除的照片仍然讀得到

`photos.routes.ts` 只檢查 `photo.userId`，沒有檢查 `photo.mealRecord.deletedAt`。病人在 App 上「刪除」一筆紀錄後，只要知道 photoId，那張照片還是拿得到。

這是刻意的設計（保留資料供研究），但**病人不知道**。同意書必須明確寫「刪除只是從你的畫面移除，資料仍會保留供研究使用」，否則這是知情同意的問題。

## 🔵 研究與倫理面的缺口

這幾項現在沒有，但你的需求 4「資料庫需要考慮未來專題要怎麼用」直接指向它們：

| 缺口 | 說明 |
|---|---|
| **沒有假名化** | `User` 表直接放 email + displayName，`Photo` 直接掛 userId。研究人員查資料就會看到真實 email。建議加 `participantCode String @unique`（如 `P001`），研究用的查詢/匯出一律只帶這個碼。 |
| **沒有同意書 / IRB 欄位** | 建議加 `consentedAt`、`consentVersion`、`irbProtocolId`、`withdrawnAt`。收案研究沒有這些欄位，口試一定會被問。 |
| **`RESEARCHER` 角色定義了但完全沒用** | 除了讀照片之外沒有任何 researcher 專用 API。你最後要分析資料時會發現只能直接連資料庫下 SQL。建議至少做一支 `GET /api/research/export`（限 RESEARCHER），輸出去識別化的 CSV / JSONL。 |
| **沒有 dataset 匯出格式** | 未來要訓練辨識模型，需要「照片檔 + 標註」的配對。現在得自己寫腳本從 uploads 資料夾撈。建議先把匯出格式定下來（例如 COCO 或簡單的 JSONL + 圖檔資料夾）。 |
| **`NutritionEstimate` 少了人工校正欄位** | 預留表設計得不錯，但少了「營養師人工標註的真值」。未來要評估模型準確率，需要 ground truth。建議加 `verifiedSodiumMg` 等一組欄位 + `verifiedBy` / `verifiedAt`。 |

## ⚙️ 部署與環境

### 12. `docker-entrypoint.sh` 用了 `prisma migrate dev`

```sh
npx prisma migrate dev --name init --skip-seed
```

`migrate dev` 是**開發專用**指令。它在偵測到資料庫與 migration 歷史不一致（drift）時，會要求重置整個資料庫。等你真的開始收病人資料之後，某次改 schema 就可能觸發這個行為。

而且每次啟動都會跑 `seed.ts`，要確認 seed 是 idempotent（用 upsert）。

**修法**：正式環境改成 `npx prisma migrate deploy`，seed 只在第一次手動跑。

### 13. 其他

- `docker-compose.yml` 把 Postgres 的 5432 port 對外開放，密碼是 `kidney_app_password` 寫死在檔案裡。本機開發沒差，放上任何有公網 IP 的機器就是災難。
- 後端沒有 `helmet`（沒有 `X-Content-Type-Options`、`HSTS` 等安全 header）。一行就能加。
- 照片上傳 API 沒有 rate limit，只有 login/register 有。
- `accessToken` / `refreshToken` 存在 `localStorage`，refresh token 有效期 30 天。一旦有 XSS，攻擊者拿到的是一個月的存取權。專題階段可接受，但要知道這件事。
- **完全沒有測試**。你的 `SECURITY_AUDIT.md` 自己也列了。至少替 `gamification.service.ts`（streak 邏輯、時區換算）寫幾個單元測試——這是全專案最容易默默算錯又最難用肉眼發現的地方。
